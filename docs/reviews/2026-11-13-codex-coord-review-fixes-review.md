## Findings

### 1. P3 — Projected jump state is timestamped before the tick that produced it

**Location:** `sim/crates/bb_game/src/live.rs:893`, `sim/crates/bb_game/src/live.rs:897`; consumed by `intercept_scan` at `:911` and `call_value` at `:1058`.

`planning_state` correctly advances a cloned fielder with production `fielder_step` until the first tick at or after his reaction gate. However, it returns `gate` as the state's start time instead of the loop's final `t`. For a reaction duration that is not a multiple of `DT`, this gives the planner a state from the future plus up to one tick of additional running time. It affects reach, fallback ETA, and confident-catch calls. The existing test's 0.02 s tolerance exceeds an entire 1/60 s tick and does not detect this error.

**Verified scenario:** A private-module probe in a `/tmp` copy used the existing fly-ball fixture, contact at 0.4 s, CF reaction **0.607 s**, and CF jump `(-speed, 0, 0)`. At the first assignment tick, approximately 0.65 s, the projection returns position **(-1.322883540, 97.536, 0)** and velocity **(-3.797067586, 0, 0)** with start time **1.007 s**. Actual movement reaches exactly that position and velocity at **1.016666667 s**. For an aerial call at **1.312 s**, aimed at that projected position, the early call reports **0.305 s** spare and tier **2**. Re-evaluating the identical prediction, intercept time, and target from the actual projected state leaves **0.295333333 s** spare, below `CALL_SLACK_S = 0.3`, and returns tier **0**. No new ball observation is involved. The corresponding 0.35 s reaction case agrees to floating-point precision. The probe also asserts that projecting changes neither the live fielder's position nor velocity.

**Suggested fix:** Return the loop's final `t` alongside the owned projected state. Retain the stationary/no-jump fast path, and add an off-grid reaction case that requires the projected state and timestamp to match actual movement, including the call-tier boundary above.

### 2. P3 — The new calibration example bypasses deterministic transcendental math

**Location:** `sim/crates/bb_game/examples/spray_by_bat_angle.rs:28`.

The example uses native `f64::atan2` rather than `bb_math::m::atan2`. This violates `CLAUDE.md` invariant 5 for newly added sim code and makes the diagnostic's intermediate angles depend on the platform math implementation. The game path itself uses the required wrapper; this finding concerns the example used to produce/refit the fixed belief coefficients.

**Verified scenario:** Instrumenting only a `/tmp` copy of the example to compare both functions over its 96-game sample found different angle bits for **835 of 5,441** fair balls. For axis coordinates `x = 0.95162827993414156`, `y = 0.30658722001356348`, native `atan2` returns bits **`3ff425605ec508c3`**, whereas `bb_math::m::atan2` returns **`3ff425605ec508c2`**. This is a one-bit intermediate discrepancy; no change to the printed rounded fit or to game outcomes was established.

**Suggested fix:** Use `bb_math::m::atan2(ax, a.y)` in the example, matching the orchestrator and the binding math contract.

## Resolution

Both findings fixed on `fix/coord-review-p3` (branched from `coord/review-fixes` at `8562924`).

1. **P3 projected jump timestamp: fixed in `29d4b67`.** `Sim::planning_state` now returns the loop's final tick time `t` with the projected state, not the gate. That tick is when the movement step actually reaches the state. All three consumers take their start time from it: `intercept_scan`, the fallback ETA in `intercept_inner`, and `call_value`. The stationary/no-jump fast path is unchanged. It still returns `self.t.max(gate)` for an unmoved fielder, whose position and velocity are correct at any time before his first step. Starting his run at the gate instead of the next tick is the planner's existing continuous-time approximation, and the no-jump calibration row depends on it. The new test `live::tests::the_projected_jump_is_timed_by_the_tick_that_produced_it` reproduces the review's case: a 0.607 s CF reaction, a full-speed jump toward left field, and a call made at the infielders' 0.25 s gate. Its expectations come from stepping the real world tick (`world_tick`) to the gate, not from the projection formula. The projected position, velocity and start time must equal that stepped state and clock exactly (`assert_eq!`), and projecting must leave the live fielder untouched. For a fly reached at that spot at gate + 0.305 s, which is 0.295 s after the tick, the early call and the call at the gate must agree and both be tier 0. On the old code the test fails at the timestamp (1.0070 vs 1.016667 s). With that assertion disabled it fails on the call: early `(2, 0.305)` vs at the gate `(0, -1.312)`, the review's boundary case exactly. The existing `plans_before_the_gate_count_the_rest_of_the_jump` tolerance was tightened from 0.02 s to 1e-9, and it passes.
2. **P3 example math: fixed in `92cfee6`.** `examples/spray_by_bat_angle.rs` now uses `bb_math::m::atan2(ax, a.y)`, and its residual square is an explicit product instead of `powi(2)`. A grep of both new examples found no other native transcendental calls (`sqrt` and `to_degrees` are exact or a multiplication). `examples/pitcher_roam.rs` has none, so it is unchanged.

**Verification.** `cd sim && cargo test --workspace --release -j 4`: all pass (bb_game lib 38 tests, including the new one). `cargo run --release -p bb_cli -- games --n 1024 --seed 5` at the default grade, before → after: runs/team-game 5.27 → 5.27; hit rates GB .409 → .409, LD .722 → .722, FB .122 → .122, PU .005 → .005; `rules warnings: {}`. The fix moves a planned start by under one tick, only for off-grid reactions before the gate. That does not move these rates at the reported precision, so `docs/calibration/2026-11-12-anticipation-review-fixes.md` is unchanged. No tuning was done.
