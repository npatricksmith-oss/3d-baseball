# Runner return after a pre-catch home touch — independent review

Reviewed **`0d81821..1c723ae`**, at checkout **`1c723ae61682a2e9fd73328ce8993a085608be52`**, after reading `CLAUDE.md` first. Locations refer to that commit. The ordinary return/cancellation/re-scoring repair works in the executed controls. Findings 1–2 are **pre-existing scoring gaps that remain in the requested “every path” audit**, not regressions introduced by this commit. Finding 3 concerns the new diagnostic.

## Findings

### 1. [P1] A winning early home touch ends the game before the catch can trigger the repair

**Location:** `sim/crates/bb_rules/src/engine.rs:576–583`, `:597–624` (`try_walk_off`); `sim/crates/bb_game/src/live.rs:1659`.

Before the catch, `retouch_required` is still false. With no outs, `outs_left >= 3` makes `try_walk_off` declare the pending winning run irrevocable even while the batted ball remains airborne. It emits `RunScored` and `GameEnded`, destroying the live play. The new runner processing cannot subsequently run because the simulation is done. A pre-catch home touch remains subject to the caught-fly retouch and appeal rules; it is not yet an irrevocable winning run. See [2026 OBR 5.09(b)(5), 5.09(c), and 5.08(a)](https://mktg.mlbstatic.com/mlb/official-information/2026-official-baseball-rules.pdf).

**Executed failing scenario:** Bottom ninth, **0–0, no outs**, H.3 (`259`) on third, H.4 batting. Deliver the pitch at 0.0 s, contact at 0.42, departure from third at 0.5, home touch at **4.5**, catch at **5.0**, return to third at **8.0**, and settlement at 10.0. At 4.5 the engine emits `RunScored { runner: 259 }` and `GameEnded { away: 0, home: 1, walk_off: true }`. Both the catch and return produce `RulesWarning { code: "game_over" }`; the final state has **zero outs**. The intended catch → retouch → hold result is **0–0, one out, H.3 on third**, with play continuing. Replaying the same probe against the parent engine produces identical output, confirming this is an unclosed path rather than a new regression.

**Suggested fix:** Specify and implement an unresolved-catch barrier to early walk-off finalization. Reevaluate the pending winning run when the flight/catch and any retouch obligations have been resolved; do not emit an irrevocable scoring/game-end event beforehand. Add this bottom-ninth sequence as a rules scenario, alongside a valid walk-off after a return and second home touch.

### 2. [P2] A third-out appeal on a preceding runner still credits the following runner’s pending run

**Location:** `sim/crates/bb_rules/src/engine.rs:651–672` (`third_out`); `docs/rules-spec.md` §6.4, referenced by the new §5.3 text.

The time-play branch counts every remaining pending home touch before the third-out timestamp. Removing the appealed runner’s own pending run in `record_out` does not remove following runners’ runs. **OBR 5.09(d) expressly includes failure to touch or retouch:** when the preceding runner becomes the third out on that appeal, following runners cannot score. The time-play treatment of an appeal on a *following* runner does not establish the converse. See [2026 OBR 5.09(d) and the 5.08 approved rulings](https://mktg.mlbstatic.com/mlb/official-information/2026-official-baseball-rules.pdf).

**Executed failing scenario:** Top sixth, **one out**, A.3 on third, A.2 on second, A.4 batting. Both runners leave early. A.2 touches third at 3.0 s; A.3 touches home at **4.0**, then A.2 at **4.5**. The catch at **5.0** makes the second out. At **7.0**, a fielder holding the ball touches third, appealing A.3 before either runner finishes returning. The engine emits `RunnerOut { runner: 3, kind: Appeal }`, then **`RunScored { runner: 2 }`** and `HalfInningEnded { runs: 1 }`. Expected: **no runs**. The parent produces the same incorrect result. This uses the supported leaving-early appeal for the actual third out; it does **not** require fourth-out appeal support.

**Suggested fix:** Correct §6.4’s blanket caught-fly-appeal time-play statement, then exclude following runners when a preceding runner’s touch/retouch appeal supplies the third out. Preserve the opposite control: a preceding runner’s otherwise eligible run can count before a third-out appeal on a following runner. Add both directions to the scenario corpus.

### 3. [P3] The diagnostic mistakes later inning/game completion for a third-out catch

**Location:** `sim/crates/bb_game/examples/home_before_catch.rs:31–36`, `:59`.

`third_out` means “any `HalfInningEnded` or `GameEnded` anywhere in this pitch’s events.” That does not establish that the **catch** was the third out. The early `continue` discards subsequent returns, appeals, re-scoring, and walk-offs, then reports “no run, no retouch owed.” It can therefore hide the very outcomes the diagnostic is supposed to inspect.

**Executed failing scenarios:** A scratch harness executed the diagnostic’s classification block verbatim on real rules-engine outputs:

- Start with one out, a runner on third touching home at 4.5 s, and a catch at 5.0 making **out two**. Appeal a trailing runner at 7.0 for out three. The events include `RunScored` for the early home toucher, but the diagnostic prints **“1 runners home before a third-out catch (no run, no retouch owed)”**, and zero live-inning cases. Appealing the home toucher instead also bypasses its “out on appeal” category.
- Bottom ninth, home trailing **1–0**, runners on second and third. The third-base runner touches home at 4.5; the catch at 5.0 makes **out one**. The second-base runner tags legally and touches home at 13.0. The early scorer retouches third at 13.5 and touches home again at 18.0. The engine correctly finishes **2–1**, with one `RunScored` per runner and **one out**. The diagnostic again prints the same “third-out catch / no run” classification because it sees `GameEnded`.

**Suggested fix:** Determine whether the catch itself supplied out three, using the starting out count and ordered out events or replaying facts with their emitted events. Process later inning/game completion through the ordinary outcome classification. Verify a retouch against the runner’s original base when assigning retouch labels.

## Resolution

Resolved 2026-11-12: all three findings fixed. `cargo test --workspace --release` passes (64 scenarios).

| # | Status | What was done |
|---|---|---|
| 1 | Fixed | `try_walk_off` no longer finalizes while the batted ball is unresolved: the ball must be caught or down fair (`grounded` and `Fair`). The check runs again after every ball fact (`BallTouched`, `BallPassedBase`, `BallSettled`, `GloveSecured`), so a winning touch made while a fly is in the air ends the game the moment it drops in fair; if it is caught, the retouch obligation holds the run until the second home touch. rules-spec §4.1 says so. Scenarios: `review-walkoff-held-until-catch` (the review's case: 0–0, one out, H.3 on third), `review-walkoff-after-return-and-second-touch`, `review-walkoff-when-the-fly-drops-fair`; all three fail on the previous engine (`game_over` at the first touch) |
| 2 | Fixed | `third_out`: when the third out is an appeal, runs by runners who started behind the appealed runner do not count (OBR 5.09(d)); runners ahead of him are still a time play. §6.4 rewritten (its blanket "an appeal on a caught fly is a time play" was wrong) and now names the fourth-out-appeal limitation the review describes. Scenarios: `review-third-out-appeal-cancels-following-run` (the review's case; fails on the previous engine) and the control `review-third-out-appeal-keeps-preceding-run` |
| 3 | Fixed | `home_before_catch` counts the play's outs in order from the out count before the pitch and takes the catch's own number; later inning or game endings go through the ordinary classification. A retouch is a touch of the runner's start base (his first `BaseLeft`). Same totals over 2,000 games (79 third-out catches; 2 returned and held) |

The verification note on `!r.retouched` (needed, but no scenario failed without it): added `review-legal-run-survives-later-touch-of-start-base`, which fails when the guard is removed.
