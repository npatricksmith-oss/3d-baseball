# Saved-play review (01011ae..36007e7)

The normal viewer decodes the companion recording without advancing a pitch. Ordinary live and replay saves write the raw `BBTL` bytes, and all 27 legacy commit inferences check out. The main blockers are selecting the correct play across a display transition and rejecting a missing, mismatched, or unusable recording reliably.

## Findings

### P1

1. **The play can change after the save dialog opens.** `client/Source/BaseballClient/BbDirector.cpp:1137` titles the dialog from `Current` and pauses the clock. At line 1185, Save reads the then-current blob and board. The handoff at lines 4255–4287 can still run with zero playback delta. Press S when the old play's hold has elapsed but the next pitch is still pending. Once that pitch is ready, a direct cut, such as after a foul into the seats, can replace `Current` while the dialog still names the old play. Also, live and history handoffs at lines 4222, 4251 and 4283 update `Current` after that tick's field and HUD were drawn. S at the start of the next tick can select the incoming play while the outgoing play is still on screen. During a walk back, the displayed frame comes from `ResetFrame` (line 3480), while the save still targets the outgoing pitch. Preserve the last presented play and board when the dialog opens, with an explicit policy for the walk back. In ordinary playback, `ShowReplay` selects the history entry and its board together (line 743), and `BbSavePlay.cpp:115` writes the complete buffer in one synchronous call. The FFI hands out an independent boxed slice per advance (`sim/crates/bb_ffi/src/lib.rs:28`), so advancing the worker does not invalidate it. The director retains history allocations until eviction or teardown. The wrong-play risk comes from selection, with no normal-length truncation or FFI lifetime defect found.
2. **A structurally valid but unusable companion can play or hang.** `client/Source/BaseballClient/BbSim.cpp:88` copies the file into owned storage and accepts whatever `FnInfo` accepts. Both FFI readers verify the `BBTL` identifier and FlatBuffer structure before accessing fields (`sim/crates/bb_ffi/src/lib.rs:359,378,453`), so ordinary short, truncated, and bad-offset files have a rejection path. That check allows absent tracks and accepts scalar floats without playback bounds. An empty timeline table can appear as a successful load with no actors. A corrupted duration that still verifies but is extremely large can hang the game thread in `NoteCatches` (`BbDirector.cpp:1443`), whose float step can stop advancing before the end. A valid companion from another play also loads without comparing its index to the TOML (`BbDirector.cpp:563,594,4015`), so a swapped file shows the wrong action under the original play label. Require the necessary tracks and bounded, finite playback values, and bind the companion to the metadata. An index check alone leaves same-index swaps across seeds undetected.
3. **An empty saved-play argument silently starts a live game.** `client/Source/BaseballClient/BbDirector.cpp:342,600` treats `-BbSavedPlay=` at the end of the command as if the flag were absent and requests a pitch. This can happen when a shell variable for the file is unset. Once the nonempty argument selects saved mode, an unreadable TOML, missing timeline key, missing companion, or structurally invalid blob takes an early return with a log and HUD error. Valid saves also return before requesting a pitch, stop at the end, and restart the same recording on R. The current sim is initialized for park and roster in all of these paths. A failed sim start returns before the viewer can show its error HUD (line 354). Animation, crew and figure preview flags can also return before the saved-play branch (lines 417–523). Those preview paths do not advance a pitch. A correctly shell-quoted path containing spaces is passed intact by `client/run.sh:28`; the installed Linux launcher restores quotes after the equals sign and `FParse::Value` reads the quoted value.

### P2

1. **The build stamp can go stale on incremental builds.** `client/Source/BaseballClient/BaseballClient.Build.cs:44,47,58` resolves the checkout correctly, and a fresh rules evaluation uses the short SHA and porcelain status from that worktree. A missing Git executable falls back to `unknown`. UBT's installed `TargetMakefile.cs:970` reuses the makefile unless a watched input disappears or is newer. The worktree's symbolic HEAD is static across commits, while the branch ref it points to is unwatched. The index catches many normal commits, but a ref-only move can leave the old SHA, and an unstaged or untracked edit can leave an old clean flag. A failed status command is also rendered as clean. Verify the stamp against Git on every build that can reuse this definition. The round-trip check currently compares the saved stamp to the same compiled value, so it cannot catch stale provenance.
2. **The headless check proves a disk round trip but bypasses the viewer entry point.** `client/Source/BaseballClient/BbDirector.cpp:827,855,871,936,961,979,1002,3281` writes under `client/Saved/SavedPlayCheck/run-<pid>`, reloads into separate storage, and compares every `SimTickS` sample from zero through the exact endpoint using `memcmp`. It takes at least one sample, even at zero duration. The second case compares a different seed's play 3 to the reloaded copy and requires its first frame to differ from the live play and the running seed's play 3. A reported mismatch requests exit status 1. However, the test installs `OtherReloaded` directly, keeps the running seed's park and roster, leaves `SavedBefore` at its default, and only checks that one rendered sample succeeds and that the index matches. The legacy case only checks parsing. A regression in `BeginPlay` that ignored the disk timeline could pass this check. A startup failure that leaves `Current` invalid never reaches the check and can hang an unattended run. Exercise the real launch path with a different seed and a legacy or broken file, and require a failure exit when startup cannot supply a test play.
3. **The current roster and park can contradict the recording.** `client/Source/BaseballClient/BbDirector.cpp:342,354,360,2428,4058` and `BbSim.cpp:42,47,62` use the saved seed to initialize today's sim, then take park geometry, names, numbers, and throw hands from that build. A roster generation change can mirror a pitcher's delivery to the opposite hand while the ball still starts from the recorded release on the original side. A fence change can put the recorded wall crossing in a visibly different place. Raw sampled frames survive these changes, but the on-screen presentation does not. The viewer also uses today's poses and camera logic.
4. **The in-park board can report a false hit total.** `client/Source/BaseballClient/BbDirector.cpp:4072` fills runs in a zeroed box summary, and `BbPark.cpp:2015` prints both totals. Opening a late-game play after earlier hits shows zero hits for both clubs even though the actual hit totals are unavailable. The same code path refreshes only at play result time, so the park's outs lamps can lag an umpire call that the HUD already displays. The HUD gets its pre-pitch base lights from proximity at release (`BbDirector.cpp:572`), so a runner leading more than four metres can be omitted. Record the board fields needed for faithful display or mark unavailable values accordingly.

### P3

1. **Some run instructions can send the owner to the wrong play.** `saved-plays/seed3647-play15-20261115-234103.toml:2` and the other legacy headers still tell the owner to run today's seed and rewind. The new header at `client/Source/BaseballClient/BbSavePlay.cpp:126` also emits an unquoted argument when writing to a directory with spaces outside the standard folder. The descriptions in `docs/data-formats.md:298` and `docs/hud.md:61` broadly match the normal viewer, with board and roster limits above. Quote the path in the example at `AGENTS.md:63`.
2. **The startup camera change affects the warming-up view.** `client/Source/BaseballClient/BbDirector.cpp:326` aims the initial camera at the same point the live camera later uses (line 3079). This is outside the requested work but also gives the legacy error screen a park backdrop. Generic `-BbShots` is wall-clock driven (line 4293), so a shot taken before the first pitch is ready can change. Park, figure and crew capture paths set their own cameras before capture (lines 4317, 4344, 4373). Motion, slide and dive captures also set their own shot cameras (lines 3934–3959). I found no other unrelated behavior change in the HUD, game mode, sim binding or launcher. The launcher now keeps a leading option instead of consuming it as the seed.
